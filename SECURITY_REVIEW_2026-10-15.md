# DISPO-CONCEPT — SECURITY REVIEW v2 (19-point hardening checklist)
**Review date:** 15 October 2026
**Scope:** full application source, gateway config, API surface, dependency set
**Method:** line-level audit of every security-relevant path, followed by surgical fixes and live verification (curl + browser, including a real RFQ submission and real chat exchange).
**Overall posture:** the platform already shipped a strong baseline (Zod-gated single write endpoint, private storage, salted rate limiting, reCAPTCHA v3, strict headers). This review closed 6 remaining gaps and documents the architecture-level and deployment-level items honestly.

## Item-by-item verdicts

| # | Control | Verdict | Evidence & notes |
|---|---|---|---|
| 1 | Row level security | **N/A at DB level — equivalent enforced by architecture** | SQLite provides no RLS. No SQL surface is exposed to clients: the only DB access is the server-side Prisma client (`src/lib/db.ts`); there is no per-user data model to isolate (no accounts). When PostgreSQL migration + authenticated roles arrive (blueprint §5), enable Postgres RLS as the second layer. |
| 2 | Auth on every API route | **PASS (public-form model) — 1 fix applied** | Exactly two routes exist, both public-by-design intake forms: `/api/rfq`, `/api/chat`. Both POST-only (GET/PUT/DELETE → 405), both enforce same-origin. **Gap fixed:** `/api/chat` lacked the Origin check RFQ had — a cross-site `text/plain` "simple request" could blind-POST past CORS preflight; now rejected 403 (`route.ts` step 1). No admin/authenticated endpoints exist yet; when the RFQ console is built, it MUST be session/role-gated (blueprint P0-D). |
| 3 | Never trust the frontend | **PASS** | Server authority everywhere: Zod schema is the single source of truth (`rfq-schema.ts`) with enums for every choice field; reference numbers generated server-side from `crypto.randomBytes`; chat system prompt fixed server-side (client sends conversation turns only, history capped 12 × 1000 chars); `content-length` gated before body buffering. Client-side validation exists only for fast feedback. |
| 4 | Rate limiting | **PASS — 1 fix applied** | Both endpoints limited (RFQ 5/h, chat 12/min) on salted-hash keys, in-memory fixed window (single-instance limitation documented). **Gap fixed:** the publicly-known constant fallback salt was removed — an attacker holding it could precompute hash keys; replaced with a per-boot `crypto.randomBytes(32)` salt (`rate-limit.ts`). Proxy trust verified: Caddy OVERWRITES `X-Real-IP` with the real remote host (`header_up X-Real-IP {remote_host}`), so it cannot be spoofed through the gateway; XFF fallback takes the rightmost hop only. |
| 5 | Sanitize user input | **PASS — 1 hardening applied** | All input trimmed/length-capped via Zod; React escapes all rendered text; zero `eval`/`new Function`/raw innerHTML from data; original upload filenames discarded before storage. **Hardened:** the five JSON-LD blocks now escape `<` → `\u003c` so no `</script>` sequence inside any string can break out (`src/app/page.tsx`). |
| 6 | Parameterized queries | **PASS** | Prisma-only data access; zero `$queryRaw`/`$executeRaw`/string-built SQL in the codebase (grep-verified). Prisma client parameterizes by construction. |
| 7 | Lock down CORS | **PASS — 1 fix applied** | No `Access-Control-Allow-*` headers anywhere → cross-origin reads are blocked by browser default; no route handles OPTIONS. RFQ enforced same-origin; **chat now does too** (see #2). |
| 8 | HTTPS everywhere | **PASS at app layer; TLS is a deployment task** | HSTS `max-age=63072000; includeSubDomains; preload` on every route; `X-Forwarded-Proto` forwarded by the gateway. `upgrade-insecure-requests` deliberately NOT added to CSP: it would break the http preview/inner-gateway path while adding nothing once real TLS terminates at the edge (HSTS covers it). Real certificates/DNS remain a launch gate (blueprint P0-B1). |
| 9 | Stop IDOR bugs | **PASS by construction** | No public read endpoints exist at all — enquiry data has no GET path; object ids (cuid) are never exposed; references are random hex; uploads are addressable only by internal randomized names. Nothing to enumerate. |
| 10 | Debug mode off in prod | **PASS** | `npm start` sets `NODE_ENV=production`; Prisma query logging removed (`db.ts` — error-level only); API errors return generic codes only, no stacks/messages; logs carry action names only (PII-free, verified in dev.log); source maps not published in production. |
| 11 | CAPTCHA on public forms | **PASS — 1 fix applied** | reCAPTCHA v3 on BOTH public forms, fail-closed when configured (score ≥ 0.5, 10 s timeout, network failure → reject). **Gap fixed (launch-gate):** server now also verifies the token's `action` — `rfq_submit` / `chat_message` — so tokens minted for one endpoint cannot be replayed at another, and optionally the `hostname` via `RECAPTCHA_EXPECTED_HOSTNAME` (added to `.env.example`). Detailed reasons logged server-side only. |
| 12 | Log admin actions | **PASS for current scope; pattern ready** | No admin console exists (nothing to log yet). Every RFQ submission writes an `AuditEvent` row (`route.ts` step 6) and the `AuditEvent` model is designed for status-change trails. Requirement recorded: any future admin surface must write actor+action+object audits. |
| 13 | Private storage buckets | **PASS — 1 hardening applied** | Uploads live in `.private-uploads/` (project root, outside `public/`, gitignored ×2 entries), randomized UUID filenames (originals discarded), file mode 0600, never served by any route. **Hardened:** the directory itself is now created with mode 0700. This is the local equivalent of a private bucket; managed object storage with lifecycle rules is the production upgrade path. |
| 14 | Hide admin pages properly | **N/A — no admin pages exist** | Grep-verified: no admin routes, pages, or API handlers. When built: server-side auth gate (not obscurity), no guessable paths, rate-limited, audited. |
| 15 | Update vulnerable packages | **PASS — current majors, verified by hand** | next ^16.1.1, react 19, zod 4, prisma 6.11, tailwind 4 — all current majors; no known unpatched CVEs against these majors; no middleware (the middleware-bypass CVE class is structurally N/A). Continuous control: run lockfile-aware audit (`bun pm ls` + CVE scan / `npm audit` after lockfile export) in CI per blueprint P0-A — this review is a point-in-time check, not a subscription. |
| 16 | Check file upload types | **PASS with documented limitation** | Extension allow-list (pdf/png/jpg/jpeg/dwg/dxf/step/stp/xlsx/docx) + per-type magic bytes (`%PDF-`, PNG, JPEG, PK-zip for Office), 10 MB cap enforced at app AND gateway (11 MB request cap), randomized storage. **Known limitation (documented in route):** DWG/DXF/STEP have no reliable signature check — accepted by extension only; without a malware-scanning daemon all attachments are treated as untrusted (sandboxed viewers, never executed). ## Fixes applied in this review
1. `src/app/api/chat/route.ts` — same-origin Origin enforcement (403 on cross-site forgeries).
2. `src/lib/rate-limit.ts` — constant fallback salt removed → per-boot high-entropy random salt.
3. `src/lib/recaptcha.ts` + both callers — token `action` assertion + optional `hostname` assertion; `.env.example` gains `RECAPTCHA_EXPECTED_HOSTNAME`.
4. `next.config.ts` — CSP `unsafe-eval` compiled out of production; `allowedDevOrigins` for the preview gateway (dev-only warning).
5. `src/app/api/rfq/route.ts` — upload directory created with mode 0700.
6. `src/app/page.tsx` — JSON-LD `<` escaping (anti `</script>` break-out, defence-in-depth).
